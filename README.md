# Task Clarifier / 任务侦查与指令构建器

`task-clarifier` 是一个面向 AI Agent 的 Skill，用来把用户的模糊需求先整理成清晰、可执行、可验收的任务指令。

它适合用在用户还没有想清楚怎么描述任务的时候：目标边界不明确、上下文不知道该给哪些、现有工具能力是否够用也不确定。这个 Skill 不会让 Agent 直接开干，而是要求它先做一轮自动侦查，再用少量关键问题把任务收敛，最后生成一份可以直接交给 Codex、Claude Code 或其他 Agent 执行的结构化指令。

## 解决的问题

很多时候，AI 任务失败不是因为模型能力不够，而是因为一开始的指令太模糊：

- “优化一下这个模块”
- “帮我看看这个怎么弄”
- “我不知道这个任务该给你看哪些文件”
- “我想让 Agent 做这件事，但不知道怎么描述”

这类请求如果直接执行，Agent 很容易猜错方向、漏掉关键文件、过早改代码，或者反复向用户追问本来可以自己查到的信息。

`task-clarifier` 的目标是把这一步标准化：

1. 先自动侦查上下文。
2. 只追问查不到且会影响结果的问题。
3. 通过 1-2 轮问题收敛任务。
4. 输出一份可执行的最终指令。

## 适用场景

这个 Skill 适合以下任务：

- 编程任务：重构、调试、迁移、优化、加功能、补测试。
- 写作任务：文章改写、资料整合、风格确认、发布前加工。
- 分析任务：需求拆解、方案比较、资料整理、调研准备。
- Agent 协作任务：把普通用户的一段自然语言需求，整理成适合交给 AI 编码工具执行的任务 brief。

尤其适合用户表达类似下面的话：

- “我不知道怎么描述这个需求。”
- “这个任务该给你看哪些文件？”
- “帮我理一下思路再让你做。”
- “先别急着改，先帮我确认该怎么做。”
- “优化一下这个模块。”
- “看看这个怎么弄。”

## 核心原则

### 先自查，再追问

Agent 能自己查到的信息，应该先自己查，不要一上来就问用户。

在编程任务里，它会优先查看目录结构、项目说明、约定文件、已有 Skill、MCP 能力、相关代码和最近改动。

在写作、分析、调研任务里，它会优先复用当前对话里的已知背景，先阅读用户提供的材料，再判断缺口。

### 只问关键问题

每一轮只问 2-4 个最关键的问题，并且问题应该是选择题或一句话可以回答的问题。

它不会一次性丢出一长串开放问题，让用户重新组织需求。

### 多轮收敛，但不无限追问

第一轮回答之后，Agent 会判断信息是否足够生成执行指令。

如果足够，就直接输出最终指令；如果不够，再进行第二轮追问。一般到第二轮应该收敛。如果第三轮还无法收敛，就应该提示用户先拆分任务，而不是继续追问。

### 输出可执行指令

最终产物不是普通建议，而是一份可以直接交给 AI Agent 执行的任务 brief，包括：

- 背景
- 具体任务
- 必须遵守的约束
- 参考材料
- 验收标准
- 是否需要先列计划再动手

## 安装方式

将 `SKILL.md` 放到你的 Codex Skills 目录中，例如：

```text
~/.codex/skills/task-clarifier/SKILL.md
```

一个推荐的仓库结构：

```text
task-clarifier/
├── README.md
└── SKILL.md
```

如果你的 Agent 工具使用不同的 Skill 目录或插件机制，请把 `SKILL.md` 的内容复制到对应的自定义 Skill 配置位置。

## 使用方式

安装后，在对话中直接描述你的模糊任务即可。例如：

```text
我想重构一下订单模块，但不知道该从哪里开始，也不知道该给你看哪些文件。
```

或者显式要求使用这个 Skill：

```text
请用 task-clarifier 帮我先梳理这个任务。
```

Agent 应该先做自动侦查，然后输出类似下面的内容：

```markdown
## 已经确认的信息（来自侦查，不用你回答）：
- 当前项目是一个 Next.js 应用。
- 订单模块主要位于 `src/modules/orders/`。
- 已有测试集中在 `tests/orders/`。

## 第一轮问题（只问当前最关键的）：
1. 这次重构的首要目标是：降低复杂度、提升性能，还是修复已知问题？
2. 你希望保持现有 UI 和接口完全不变吗？
3. 验收方式以现有测试通过为准，还是需要新增测试覆盖核心流程？
```

当用户回答后，Agent 再输出一份明确的执行指令。

## 最终输出示例

```markdown
## 背景
当前项目的订单模块负责订单列表、订单详情和订单状态更新。用户希望先降低维护成本，不改变现有业务行为。

## 具体任务
请重构 `src/modules/orders/` 下的订单状态处理逻辑，把重复的状态判断集中到一个明确的 helper 中，并保持现有页面行为不变。

## 必须遵守的约束
- 不改变现有接口返回结构。
- 不调整 UI 文案和交互流程。
- 不做与订单状态无关的重构。
- 如果发现现有行为不一致，先记录问题，不要自行改业务规则。

## 参考材料
- `src/modules/orders/`
- `src/api/orders.ts`
- `tests/orders/`

## 验收标准
- 现有订单相关测试全部通过。
- 新增至少 1 个覆盖状态判断 helper 的单元测试。
- 重构后重复状态判断明显减少。

## 执行要求
请先列出执行计划，确认涉及文件后再开始修改。
```

## 工作流

`task-clarifier` 内置了三个步骤。

### Step 0：自动侦查

先查能查到的上下文，不把这些问题丢给用户。

编程任务会检查：

- 相关目录结构
- `README`、`CLAUDE.md`、`.cursorrules` 等项目约定
- 已有 Skill 或 MCP 能力
- 相关代码和最近改动
- 测试用例和配置文件

通用任务会检查：

- 当前对话里已有的背景
- 用户上传或粘贴的材料
- 受众、用途、格式、风格等已知约束

### Step 1：整理事实并提出第一轮问题

先告诉用户已经确认了什么，再问当前最关键的问题。问题需要短、具体、容易回答。

### Step 2：根据回答继续收敛

根据用户回答判断是否还需要第二轮问题。只有第一轮回答引出了新的关键缺口，才继续追问。

### Step 3：生成最终可执行指令

把已确认的信息整理成结构化任务 brief，让另一个 Agent 可以直接执行。

## 能力缺口处理

如果任务需要当前环境没有的能力，例如访问某个业务系统、读取特殊格式文件、调用未连接的 MCP，Skill 会要求 Agent 明确提出能力缺口，并给用户两个选择：

- 先补齐能力后再执行。
- 降级为当前能力范围内的替代方案，并说明会损失什么。

这样可以避免 Agent 假装能做，最后交付一个不可靠的结果。

## 和普通提示词的区别

普通提示词通常只告诉 Agent “你要多问问题”。`task-clarifier` 更强调执行顺序：

- 先自查，不把上下文收集工作推给用户。
- 问题分批，不一次性制造压力。
- 每轮问题都必须服务于任务收敛。
- 最终输出必须能直接进入执行阶段。
- 对能力缺口要显式暴露，不能悄悄降级。

## 自定义建议

你可以根据自己的工作流调整以下部分：

- 把 `CLAUDE.md`、`.cursorrules` 替换成你常用工具的约定文件。
- 增加你常用技术栈的专项检查项。
- 增加团队内部的验收标准模板。
- 为写作、数据分析、产品需求等不同任务添加专门的问题模板。
